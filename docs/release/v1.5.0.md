# v1.5.0 — Passkeys and One-Time Passwords

**Release date:** 2026-11-08
**Status:** stable minor release. Additive only; `cargo-semver-checks`
against 1.4.0 reports no semver break. No wire-format change. MSRV
stays 1.85. The default build is unchanged.

---

## What this release is

Two-factor authentication needs two things from a crypto library:
authenticator-app codes, and passkey assertion checks. 1.5.0 adds both,
behind opt-in features on the same AWS-LC backend as the `sign-*`
features:

```toml
[dependencies]
crypt-io = { version = "1.5", features = ["otp", "sign-p256", "sign-ed25519", "sign-rsa"] }
```

```rust
use crypt_io::{otp, sign::CosePublicKey};

// Authenticator apps (RFC 6238): accept 30 s of drift, keep the step.
let step = otp::totp_check(&secret, typed_code, unix_seconds, 6, 1)?;
// reject if step <= last_used_step; then store step

// Passkeys (WebAuthn): the stored COSE credential key.
let key = CosePublicKey::from_cose_key(&credential_public_key)?;   // ES256, EdDSA or RS256
key.check(&signed_data, &signature)?;     // authenticatorData || SHA-256(clientDataJSON)
```

## One-time passwords (feature `otp`)

- `otp::hotp(secret, counter, digits)` (RFC 4226) and
  `otp::totp(secret, unix_seconds, digits)` (RFC 6238: 30-second step,
  T0 = 0) give the code an authenticator app shows.
- `otp::totp_check(secret, code, unix_seconds, digits, window)` and
  `otp::hotp_check(secret, code, counter, digits, look_ahead)` take the
  code as typed, compute every candidate in the window and compare all
  of them in constant time. They return the matched step or counter:
  store it and refuse any later code whose step is not greater, because
  a TOTP code is otherwise valid for its whole step and window.
- Limits: secrets of at least 16 bytes (RFC 4226 requires 128 bits),
  6 to 8 digits, a window of at most 10 (`OTP_MAX_WINDOW`). A wrong or
  malformed code is `Error::AuthenticationFailed`; bad parameters are
  `Error::InvalidInput`.

**HMAC-SHA1 is legacy.** RFC 4226 and 6238, and every authenticator
app, use HMAC-SHA1. HMAC does not rely on SHA-1's collision resistance,
which is broken, so the construction is still sound for OTPs. It lives
only in `otp`, never in `mac`, and `otp::hmac_sha1_legacy` exists only
for OTP variants the functions above do not cover. Use HMAC-SHA256 for
everything else.

Not covered: TOTP with SHA-256 / SHA-512 or a step other than 30
seconds (authenticator apps rarely support them; build them on
`hmac_sha1_legacy` / `mac::hmac_sha256` if needed), and base32 decoding
of `otpauth://` secrets.

## ECDSA P-256, verify only (feature `sign-p256`)

`sign::EcdsaP256PublicKey`:

- `from_sec1` (65-byte uncompressed or 33-byte compressed point),
  `from_coordinates(x, y)` (COSE, JWK) and `from_der` (SPKI). The point
  is validated on parse; another curve is refused.
- `check_sha256(message, der_signature)`: the WebAuthn, COSE-in-WebAuthn
  and X.509 form.
- `check_sha256_fixed(message, r_s)`: the 64-byte JOSE `ES256` form
  (RFC 7518).

crypt-io does not sign with ECDSA. ECDSA signing needs a fresh secret
nonce per signature, and Ed25519 avoids that failure mode; P-256
support is for keys other parties choose, which for passkeys is most
of them.

## WebAuthn credential keys

`sign::CosePublicKey::from_cose_key` parses a credential's
`credentialPublicKey` (RFC 9052 `COSE_Key`) and returns `EcdsaP256`,
`Ed25519` or `Rsa`, depending on the key and the features enabled.
`check(message, signature)` dispatches to the key's algorithm: a DER
signature for `ES256`, Ed25519 for `EdDSA`, PKCS#1 v1.5 SHA-256 for
`RS256` (Windows Hello). `RsaPublicKey::from_components(n, e)` is new
for this, and is also useful for JWK keys.

The parser takes bytes an authenticator controls, so it is strict:
exactly one definite-length CBOR map, integer labels (text labels
skipped), no tags, no duplicate labels, no trailing bytes, at most 16
parameters, and nesting at most 4 deep inside skipped values. `kty` and
`alg` must be present and agree (`ES256` with `crv` P-256 and 32-byte
coordinates, `EdDSA` with `crv` Ed25519, `RS256` with 2048- to
8192-bit `n`). Errors:

- `Error::Sign("COSE key: unsupported algorithm")` for `ES384`,
  `ES512`, Ed448, `PS256` and the rest;
- `Error::AlgorithmNotEnabled` for a supported algorithm whose feature
  is off;
- `Error::Sign` with the reason for malformed or inconsistent keys;
- `Error::AuthenticationFailed` from `check` for a signature that does
  not match.

The relying-party checks (challenge, origin, RP ID hash, flags,
signature counter) are the caller's: crypt-io checks the signature.

and RFC 6238 value with Python's `hmac`, and the RS256 WebAuthn
signature with `pow()`, before writing them.

## Compatibility

- **API:** additive. New `otp` module; `EcdsaP256PublicKey`,
  `CosePublicKey` and `RsaPublicKey::from_components` in `sign`.
- **Features:** new `otp` and `sign-p256`; `sign-all` now includes
  `sign-p256`. Both pull AWS-LC and `std`, like the other `sign-*`
  features (C compiler; NASM or `prebuilt-nasm` on Windows x86-64).
- **MSRV:** Rust 1.85, unchanged. **Dependencies:** unchanged; no
  `hmac` / `hkdf` crates.
