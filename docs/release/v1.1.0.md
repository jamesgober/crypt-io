# v1.1.0 — Stream v2, check APIs, no_std

**Release date:** 2026-10-09
**Status:** stable minor release. Additive only; `cargo-semver-checks`
against 1.0.1 confirms a minor update is enough. Everything 1.0.x
encrypted decrypts unchanged.

---

## What this release is

1.0.1 fixed what a security review of 1.0.0 found that could be fixed
without new API. 1.1.0 does the rest:

- a stream format that gives every stream its own key,
- MAC and password checks that cannot be ignored with `?`,
- a `no_std` build that actually works,
- XChaCha20-Poly1305 for keys that encrypt a very large number of
  messages,
- control over which Argon2 hashes are accepted,
- wiping of AES round keys and HMAC state,
- and a set of smaller hygiene and error-reporting fixes.

---

## Before you upgrade: mixed fleets

1.1.0 writes **stream format v2** by default (`StreamEncryptor::new`,
`new_with_chunk_size`, `stream::encrypt_file`). crypt-io 1.0.x cannot
read v2; it returns `InvalidCiphertext("unsupported stream version:
0x02 ...")`. If any reader still runs 1.0.x, keep writing v1 until it
is upgraded:

```rust
use crypt_io::stream::{StreamEncryptor, StreamFormat, DEFAULT_CHUNK_SIZE_LOG2};
let (enc, header) = StreamEncryptor::new_with_format(
    &key, algorithm, DEFAULT_CHUNK_SIZE_LOG2, StreamFormat::V1)?;
```

1.1 reads both formats, so upgrade readers first.

## Stream format v2

v1 encrypted every stream directly under your key, kept apart only by
a random 56-bit nonce prefix. Two streams with the same prefix reuse
nonces (and for AES-256-GCM expose the GHASH key), so one key was good
for about 4,096 streams.

A v2 stream has a 32-byte random salt right after its 24-byte header,
and its chunks are encrypted under

```text
HKDF-SHA256(ikm = key, salt = salt, info = "crypt-io stream v2" || header)
```

which also produces the nonce prefix. Two streams share nonces only
if their 256-bit salts collide, so there is no practical limit on
streams per key. The header and salt are authenticated with every
chunk; v2 headers must have zero reserved bytes.

The API does not change: the encryptor still returns a 24-byte
header, and its first output starts with the salt; the decryptor
still takes the 24-byte header and reads the salt from `update`. Code
that writes the header and then every output in order needs no
changes. The spec and test vectors (generated by an independent
implementation) are in [`docs/FILE_FORMAT.md`](../FILE_FORMAT.md).

New: `StreamFormat`, `StreamEncryptor::new_with_format`,
`algorithm()` / `format()` on both stream types, `stream::SALT_LEN`.

## `*_check`: a mismatch is an error

The 1.0 `*_verify` functions return `Ok(false)` on a mismatch, so
`hmac_sha256_verify(key, data, tag)?;` compiles and accepts forged
tags, and `argon2_verify(..)?;` logs everyone in. New functions
return `Err(Error::AuthenticationFailed)` instead:

| Use | Instead of |
|---|---|
| `mac::hmac_sha256_check` | `mac::hmac_sha256_verify` |
| `mac::hmac_sha512_check` | `mac::hmac_sha512_verify` |
| `mac::blake3_keyed_check` | `mac::blake3_keyed_verify` |
| `kdf::argon2_check` / `argon2_check_with_policy` | `kdf::argon2_verify` |
| `HmacSha256::check`, `HmacSha512::check`, `Blake3Mac::check` | `verify` (still fine: it returns a `#[must_use]` `bool`) |

The old functions are deprecated (you will get a warning at each call
site) and keep working for all of 1.x. `Tag<N>` wraps a tag so that
`==` is constant-time, for code that compares tags itself.

## `no_std`

With `default-features = false` the crate is `no_std` + `alloc`. CI
builds it for `thumbv7em-none-eabihf` on stable and Rust 1.85.
Hashing, MACs, HKDF, Argon2 checks, every decrypt path,
`Crypt::open` and `StreamDecryptor` need nothing else. Encryption,
sealing, `StreamEncryptor`, `argon2_hash*` and `generate_key` need a
random source: enable the new `getrandom` feature (on bare metal,
register a `getrandom` custom backend backed by your hardware RNG).
Details: [`docs/PLATFORM-NOTES.md`](../PLATFORM-NOTES.md#no_std-110).

This also answers issue #3: `error-forge` was removed in 1.0.1, and
1.1.0 removes the remaining `std` requirements.

## XChaCha20-Poly1305 and the sealed format

- `Algorithm::XChaCha20Poly1305` / `Crypt::xchacha20_poly1305()`: a
  192-bit random nonce, so the 2^32-messages-per-key limit of
  ChaCha20-Poly1305 and AES-256-GCM does not apply. Works in
  single-shot, sealed and stream (v2) form.
- `Crypt::seal` / `open`: `0x01 || algorithm || nonce || ciphertext ||
  tag`, with the two header bytes authenticated. `open` reads the
  algorithm from the buffer, so you can change algorithms without
  tracking which one wrote each record.

## Argon2 policy

`argon2_check` applies the 1.0.1 limits (argon2id only, `m` ≤ 1 GiB,
`t` ≤ 64, `p` ≤ 16). `Argon2Policy` changes them:

- raise the caps if you stored hashes with higher costs before 1.0.1
  (those hashes fail with `Error::Kdf` on 1.0.1),
- set minimums so a cheap hash planted in your store is rejected,
- allow `argon2i` / `argon2d` while migrating.

`Argon2Params::validate()` checks custom parameters against the OWASP
minimums. `argon2_hash_with_policy` hashes under a policy.

## Memory hygiene

- With `zeroize` (default): AES round keys (`aes` is now a direct
  dependency with `zeroize`) and HMAC / SHA-2 state (`hmac` 0.13,
  `sha2` 0.11) are wiped on drop. A test checks that a dropped
  HMAC leaves only zeros.
- Growing a decrypt buffer no longer leaves the old plaintext in
  freed memory.
- `generate_key()`, `Crypt::decrypt_zeroizing`, `kdf::hkdf_*_into`
  and `hash::blake3_long_into` keep secret output out of plain
  `Vec`s.
- Still not wiped: the GHASH key inside `polyval` 0.6. The fix needs
  `aes-gcm` 0.11, which measured about 40% slower on 64-byte messages
  and pulls an `aes` release that needs Rust 1.89; see
  [`docs/SECURITY.md`](../SECURITY.md).

## Errors

New variants `Error::Io`, `Error::InvalidInput` and
`Error::LimitExceeded`. Cases that used to be reported as something
else now use them:

| Case | 1.0.x | 1.1.0 |
|---|---|---|
| File-helper I/O failure | `Mac` | `Io` |
| Same file as input and output | `Mac` | `InvalidInput` |
| Stream chunk size out of range | `InvalidCiphertext` | `InvalidInput` |
| Plaintext / AAD too long | `AuthenticationFailed` | `LimitExceeded` |
| Stream past 2^32 chunks | `InvalidCiphertext` | `LimitExceeded` |

If you match on those variants for these cases, update the match.

## Performance

Interleaved A/B against 1.0.1 in one process:

- small streams 3.5–4.5× faster (drop wiped the whole 64 KiB buffer
  capacity; it now wipes only what was used), 10 MiB stream decrypt
  about 1.4× faster, stream encrypt 3–12% faster;
- `Crypt::encrypt` 1.3–2× faster from 64 KiB up;
- `hmac_sha256_check` 15–40% faster than `hmac_sha256_verify`;
- SHA-256 on small inputs and HKDF-SHA256: 6–35 ns slower per call
  (the `sha2` 0.11 upgrade that HMAC state wiping needs, plus the
  wiping). Everything else within noise.

Full table: [`docs/PERFORMANCE.md`](../PERFORMANCE.md).

## Compatibility

- **API:** additive. Four functions deprecated, none removed.
- **Wire formats:** v1 streams and 1.0 single-shot buffers decrypt
  unchanged. New output is stream v2 (see "mixed fleets" above).
- **MSRV:** Rust 1.85, unchanged. On 1.85 / 1.86 with resolver 2,
  run `cargo update -p ctutils --precise 0.4.2`.
- **Default features:** unchanged. New optional feature `getrandom`.
- **Dependencies:** `hmac` 0.13, `sha2` 0.11, `hkdf` 0.13; new `aes`,
  `subtle`, optional `getrandom`. None appear in the public API.
