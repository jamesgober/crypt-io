# v1.2.0 — Public Wipe

**Release date:** 2026-10-23
**Status:** stable minor release. Additive only; `cargo-semver-checks`
against 1.1.0 reports no semver break. No wire-format change.

---

## What this release is

crypt-io has wiped its own key copies and plaintext buffers with
volatile writes since 1.0.1, through a private helper. 1.2.0 makes
that helper public, so code that keeps secrets in plain byte buffers
can clear them with the same guarantee, without writing `unsafe` and
without taking its own dependency on `zeroize`.

```rust
let mut token = *b"session token";
crypt_io::wipe(&mut token);
assert!(token.iter().all(|&b| b == 0));

let mut body = Vec::with_capacity(4096);
body.extend_from_slice(b"response body");
crypt_io::wipe_vec(&mut body);
assert!(body.is_empty());
assert_eq!(body.capacity(), 4096);
```

---

## `wipe` and `wipe_vec`

- `crypt_io::wipe(bytes: &mut [u8])` overwrites every byte of the
  slice with zeros. Only the slice itself is touched.
- `crypt_io::wipe_vec(v: &mut Vec<u8>)` overwrites the whole
  allocation: the length and the spare capacity, where bytes from
  before a `truncate` or `clear` can still sit. It then sets the
  length to 0 and keeps the allocation, so the buffer can be reused
  without a new allocation.

**The guarantee depends on the `zeroize` feature.** With `zeroize`
(on by default) the writes go through the `zeroize` crate's volatile
writes, which the compiler cannot remove even when the buffer is
never read again. Without `zeroize` they are plain writes followed by
`core::hint::black_box`. That stops the optimiser in practice but is
not a guarantee, so keep `zeroize` on for anything secret.

**What neither function can reach:** copies made elsewhere. A `Vec`
that grew with `push` or `reserve` may have left its old contents in
freed memory, and a value moved on the stack leaves its old bytes
behind. Size secret buffers up front with `Vec::with_capacity`.

## Feature sets and `no_std`

Both functions are compiled with every feature set, including
`default-features = false`, and need no `std`. The smallest useful
set for a crate that wants the volatile wipe and the keyed BLAKE3
MAC is:

```toml
[dependencies]
crypt-io = { version = "1.2", default-features = false, features = ["zeroize", "mac-blake3"] }
```

The keyed BLAKE3 MAC (`mac::blake3_keyed`, `blake3_keyed_check`,
`Blake3Mac`) needs nothing from `std`: it works in this set exactly
as with default features, and its state is wiped on drop under
`zeroize`. Without `std` BLAKE3 picks its SIMD backend at compile
time (from the target features) instead of at run time; build with
`-C target-cpu=...` or the `std` feature if you want run-time
detection of AVX2 / AVX-512 on x86. See
[`docs/PLATFORM-NOTES.md`](../PLATFORM-NOTES.md).

CI now builds this set for `thumbv7em-none-eabihf` and with
`-Zminimal-versions`, and runs the unit and doc tests for it and for
`mac-blake3` without `zeroize` (the fallback path).

## Internal change

The stream types and the format v2 key schedule wiped their key
material through a private `wipe_bytes`. They now call the public
`wipe`, which has the same body. No behaviour change.

---

## Compatibility

- **API:** additive. Two new functions at the crate root.
- **Wire formats:** unchanged.
- **MSRV:** Rust 1.85, unchanged. On 1.85 / 1.86 with resolver 2,
  run `cargo update -p ctutils --precise 0.4.2`.
- **Default features:** unchanged.
- **Dependencies:** unchanged.
