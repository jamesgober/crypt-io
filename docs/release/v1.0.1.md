# v1.0.1 — Security Patch

**Release date:** 2026-10-08
**Status:** stable patch release. No public API or wire-format
change; `cargo-semver-checks` against 1.0.0 reports no semver update
required. Upgrading is recommended for all 1.0.0 users.

---

## What this release is

A security review of 1.0.0 found that the AEAD core is sound (fresh
OS-CSPRNG nonces, tag checked before plaintext is released, STREAM
framing catches truncation, reordering and tampering), but that
several protections around it were missing or weaker than the
documentation said. 1.0.1 fixes everything that can be fixed without
an API or format change, and corrects the documentation where 1.0.0
overstated its guarantees.

---

## Security fixes

### Keys printed by `Debug`

`StreamEncryptor` and `StreamDecryptor` derived `Debug`, so `{:?}`
printed the raw 32-byte key and any buffered plaintext. Both now
print only the algorithm, chunk size, counter and buffered length.

### The `zeroize` feature now does something

In 1.0.0 the default `zeroize` feature was never used. In 1.0.1:

- the stream types overwrite their key copy and internal buffer on
  drop;
- `Blake3Mac` wipes its keyed state on drop;
- the feature turns on the upstream `zeroize` support in `aes-gcm`,
  `argon2` and `blake3`.

Still not wiped in 1.0.x: AES round keys inside the `aes` crate,
HMAC state, and the plaintext `Vec`s crypt-io returns to you. Wrap
those in `zeroize::Zeroizing` if you need it.

### `aes-gcm` floor raised past RUSTSEC-2023-0096

`aes-gcm = "0.10"` allowed 0.10.0 to 0.10.2, which decrypt in place
before checking the tag. The floor is now `0.10.3`. The `blake3`
floor is now `1.5`. A `-Zminimal-versions` build is checked in CI.

### `_into` buffers

- `decrypt_into` / `decrypt_with_aad_into` clear `out` before any
  check. 1.0.0 returned the previous message's plaintext together
  with `InvalidKey` or `InvalidCiphertext`.
- On `AuthenticationFailed` the whole allocation, spare capacity
  included, is overwritten with zeros. 1.0.0 only called
  `Vec::clear()`, which leaves the bytes in place.
- `encrypt_into` wipes `out` if the upstream cipher rejects an input
  after the plaintext was copied in.
- `StreamDecryptor::update_into` restores `out` to its entry length
  (and wipes what it appended) when a chunk fails.

### `stream::decrypt_file` writes only authenticated output

1.0.0 wrote plaintext straight to the destination; a truncated or
tampered file returned an error but left the verified prefix on
disk, world-readable under the default umask. 1.0.1 writes to a new
temporary file next to the destination (mode `0600` on Unix),
`fsync`s it, and renames it into place only after the final chunk
authenticates. On error the temporary file is overwritten and
removed, and the destination is left untouched.

### `argon2_verify` limits

The cost parameters and variant of a PHC string were trusted as-is,
so a hostile or corrupted hash could make each login allocate
gigabytes or run for minutes, or downgrade to `argon2d`.
`argon2_verify` now rejects with `Error::Kdf`, before doing any work:

- any variant other than `argon2id`;
- `m` above 1 GiB, `t` above 64 or `p` above 16.

crypt-io has only ever produced `$argon2id$v=19$` hashes.
`argon2_hash_with_params` enforces the same limits, so everything it
produces can be verified.

## Other fixes

- **`StreamDecryptor::update` is linear.** 1.0.0 was quadratic when
  a large input was fed in one call (32 MiB at 1 KiB chunks: 46 s;
  1.0.1: 66 ms).
- **`encrypt_file(p, p, ..)`** no longer destroys `p`. Both file
  helpers reject an output path that resolves to the input file.
- **Unused dependencies removed:** `error-forge` (non-optional in
  1.0.0), `log-io`, `metrics-lib`, `async-trait`. The `logging`,
  `metrics` and `async-trait` features are kept as empty features.

---

## Documentation corrections

- **`verify(..)?;` accepts forgeries.** `hmac_sha256_verify`,
  `hmac_sha512_verify` and `argon2_verify` return `Ok(false)` on a
  mismatch. Always write `if !verify(..)? { reject }`. All examples
  now do.
- **Nonce limits.** At most 2^32 single-shot messages per key (the
  docs said 2^48, which is where a collision becomes likely), and
  about 2^12 (4,096) streams or files per key unless you derive a
  per-file key with HKDF.
- **No `no_std` in 1.0.x.** The earlier claim was wrong for every
  feature combination.
- Removed: the comparison of the stream format to `age`, references
  to a non-existent `rust-toolchain.toml`, the "early scaffolding"
  status line, and the `error-forge` "error metadata" claim.
- `StreamDecryptor::update` output is documented as not
  end-authenticated until `finalize` succeeds.

## Behaviour changes to check when upgrading

- `decrypt_file` output on Unix now has mode `0600`.
- `encrypt_file` / `decrypt_file` with the same input and output path
  return `Error::Mac` instead of running.
- `argon2_verify` returns `Error::Kdf` (not `Ok(..)`) for non-Argon2id
  hashes and for hashes above the limits; `argon2_hash_with_params`
  returns `Error::Kdf` for parameters above the limits.
- `StreamDecryptor::update_into` leaves `out` as it was on entry when
  it fails.

---

## What's NOT in 1.0.1

These need an API or format addition and are planned for 1.1:

- A stream format with a per-stream subkey, removing the
  streams-per-key limit. 1.x will keep decrypting the current format.
- `Result<()>`-returning `*_check` verifiers, and `#[must_use]` on the
  `bool` verifiers.
- Real `no_std` support.

---

## Compatibility & build

- **API and wire formats unchanged.** Files and messages written by
  1.0.0 decrypt with 1.0.1 and the other way round.
- **Dependencies:** four unused ones removed; floors raised for
  `aes-gcm` (0.10.3) and `blake3` (1.5).
- **MSRV unchanged:** Rust 1.85 (edition 2024).
- **Default features unchanged.**
