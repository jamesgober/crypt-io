# v1.2.2 — No ctutils (RUSTSEC-2026-0385)

**Release date:** 2026-10-26
**Status:** stable security patch. No public API, output or
wire-format change. MSRV stays 1.85.

---

## What this release is

[RUSTSEC-2026-0385](https://rustsec.org/advisories/RUSTSEC-2026-0385.html)
(2026-10-23) affects `ctutils` before 0.4.4: its `Choice` mask
generation could compile to a branch on common platforms, and its
`u128` comparisons branched on 32-bit targets. Branches on secret
values can leak them through timing.

crypt-io reached `ctutils` through `hmac` 0.13, which turns on
`digest`'s `mac` feature (`Mac::verify_slice` compares with
`ctutils::CtEq`). Every fixed `ctutils` release declares
`rust-version = "1.87"`, so Cargo's MSRV-aware resolver kept 0.4.2 for
any build whose effective Rust version was 1.85 or 1.86. No
`ctutils` version is both fixed and compatible with crypt-io's MSRV.

1.2.2 removes the `hmac` and `hkdf` dependencies and builds HMAC and
HKDF in crypt-io over the same RustCrypto `sha2` hashes. Nothing in
the dependency graph pulls in `ctutils` any more, for any feature set,
target or toolchain.

---

## Who was affected

Measured with `cargo tree -e normal -i ctutils` on fresh consumer
crates depending on crypt-io 1.2.1, for nine feature sets, toolchains
1.85, 1.86 and 1.99, with and without `rust-version = "1.85"` in the
consumer:

| Resolver | Effective Rust version | `ctutils` resolved |
|---|---|---|
| MSRV-aware (edition 2024, or `resolver = "3"`, or `incompatible-rust-versions = "fallback"`) | 1.85 or 1.86 (the toolchain, or the workspace's `rust-version`, on **any** toolchain) | **0.4.2, vulnerable** |
| MSRV-aware | 1.87 or later | 0.4.6, fixed |
| Not MSRV-aware (edition 2021 default) | any | 0.4.6, fixed (Rust 1.85 / 1.86 refuse to build it, as they refuse `sha2` 0.11.1, which needs 1.88) |

Feature sets that pulled `ctutils` in: any with `mac-hmac`,
`kdf-hkdf` or `stream`, so the default features and `preset-all` too.
Feature sets that did not: `hash-sha2` on its own (`sha2` does not use
`digest`'s `mac` feature), `zeroize,mac-blake3` (bouncer-io's set),
AEAD, BLAKE3 and Argon2 sets, `preset-minimal`.

crypt-io's own `Cargo.lock` and `fuzz/Cargo.lock` had 0.4.2 as well.

The affected code was reached: `hmac_sha256_check`,
`hmac_sha512_check`, the deprecated `_verify` functions and
`HmacSha256::verify` / `check` (and the SHA-512 forms) all ended in
`verify_slice`. HMAC tag computation, HKDF and the stream format did
not compare anything; `Tag::ct_eq` and the BLAKE3 MAC use `subtle`.

**What to do:** update to 1.2.2 (`cargo update -p crypt-io`). A
lockfile that still lists `ctutils` 0.4.2 only because of crypt-io
loses it on that update.

## How HMAC and HKDF work now

`src/hmac_core.rs`, about 150 lines:

- **HMAC** (RFC 2104): a key longer than the block (64 bytes for
  SHA-256, 128 for SHA-512) is hashed first, a shorter one is padded
  with zeros; the inner hash absorbs `K ^ ipad`, the outer hash
  `K ^ opad`. The tag is `H(K ^ opad || H(K ^ ipad || data))`. Both
  hash states are prepared once per key, as in the `hmac` crate, so
  streaming and cloning work as before.
- **Tag checks** compute the tag and compare it with
  `subtle::ConstantTimeEq`, a `u64` at a time: `subtle`'s slice
  comparison puts an optimisation barrier after every byte, which
  made a 1 KiB check about 30% slower than 1.2.1 in a first
  measurement; words need an eighth of the barriers. A tag of the
  wrong length never matches.
- **HKDF** (RFC 5869): extract `PRK = HMAC(salt, IKM)`, with an absent
  salt as `HashLen` zero bytes; expand
  `T(i) = HMAC(PRK, T(i-1) || info || i)` up to 255 blocks. The
  stream format's v2 subkey derivation uses the same function.
- **Wiping:** the padded key block, a hashed long key, the inner
  hash, the PRK and the last `T(i)` are wiped before they go out of
  scope. With `zeroize` (default on) the hash states are wiped on
  drop by `sha2`, so the existing test that a dropped `HmacSha256` /
  `HmacSha512` leaves only zeros still passes.

SHA-256 and SHA-512 themselves still come from `sha2` 0.11.

## Proof the output did not change

New `tests/hmac_hkdf.rs`, through the public API:

- all six RFC 4231 cases with full-length tags, for HMAC-SHA256 and
  HMAC-SHA512 (cases 6 and 7 use a 131-byte key, longer than both
  blocks), one-shot, streamed one byte at a time, and through every
  check form;
- RFC 5869 cases 1 to 3 (the SHA-256 ones), and an HKDF-SHA512
  vector;
- every single-bit flip of a tag, and tags of the wrong length;
- a grid of 3,393 HMAC inputs per hash (key lengths 0 to 260, data
  lengths around the block sizes) and 840 HKDF inputs per hash
  (IKM, salt, info and output lengths, up to the 255-block maximum),
  checked against digests computed with Python's `hmac` and
  `hashlib`.

The grid test was written first and passed against 1.2.1's `hmac` /
`hkdf` crates, then against the new code. The frozen stream KATs in
`tests/kat.rs` (format v2 derives its subkey with HKDF-SHA256) pass
unchanged.

## Performance

Criterion, Windows, Rust 1.99, same machine and session for both
versions (a shared machine, so a few percent is noise). Median times:

| Benchmark | 1.2.1 (`hmac` / `hkdf` crates) | 1.2.2 |
|---|---|---|
| `hmac_sha256` 64 B | 174-190 ns | 194-199 ns |
| `hmac_sha256` 1 KiB | 588-598 ns | 585 ns |
| `hmac_sha256` 64 KiB | 29.6 µs | 26.0 µs |
| `hmac_sha512` 64 B | 827 ns | 760 ns |
| `hmac_sha512` 64 KiB | 91.8 µs | 82.6 µs |
| `hmac_sha256_check` 1 KiB | 567-599 ns | 608-614 ns |
| `hkdf_sha256` 32 B out | 351 ns | 377 ns |
| `hkdf_sha256` 128 B out | 702 ns | 710 ns |
| `hkdf_sha512` 64 B out | 1.81 µs | 1.65 µs |

Short inputs pay about 10-20 ns for the extra wiping of the key block
and the inner hash; long inputs are as fast or faster.

## CI guard

The audit job now runs on four lockfiles: the committed one, and
fresh resolutions as a Rust 1.85 user, a Rust 1.86 user and a
newest-versions user get them (the 1.85 / 1.86 runs set
`rust-version` and resolve with
`CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback`). Each run fails
by name if the lockfile has any `ctutils` below 0.4.4, independent of
the advisory database, and then runs `cargo audit`. The lockfile
holds every package of every feature and target, so each run covers
every feature set.

Checked locally against the 1.2.1 tree: the guard and `cargo audit`
fail on the committed, 1.85 and 1.86 lockfiles. On 1.2.2 all four are
clean.

## Other changes

- `Error::Mac` can no longer come out of the HMAC functions; their
  `Result` signatures stay for 1.x compatibility.
- `HmacSha256` / `HmacSha512` `Debug` output no longer includes hash
  state.
- Docs (`API.md`, `ARCHITECTURE.md`, `SECURITY.md`,
  `PERFORMANCE.md`) no longer describe the `hmac` / `hkdf` crates.
