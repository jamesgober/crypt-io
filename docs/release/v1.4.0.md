# v1.4.0 — Signature Checks

**Release date:** 2026-11-05
**Status:** stable minor release. Additive only; `cargo-semver-checks`
against 1.3.0 reports no semver break. No wire-format change. MSRV
stays 1.85. The default build is unchanged.

---

## What this release is

1.3.0 added signing. 1.4.0 adds the other half: checking Ed25519 and
RSA PKCS#1 v1.5 (SHA-256) signatures, for DKIM verification of inbound
mail (RFC 6376, RFC 8463) and JOSE `EdDSA` / `RS256` tokens. Same
features as signing, still off by default:

```toml
[dependencies]
crypt-io = { version = "1.4", features = ["sign-ed25519", "sign-rsa"] }
```

```rust
use crypt_io::sign::{Ed25519PublicKey, RsaPublicKey};

// Ed25519: the 32 bytes of a DKIM p= record or a JWK x member.
let ed = Ed25519PublicKey::from_bytes(&p_value)?;
ed.check(&header_hash, &b_value)?;            // Err(AuthenticationFailed) if forged

// RSA: SubjectPublicKeyInfo (DKIM p=, PEM body) or PKCS#1.
let rsa = RsaPublicKey::from_der(&spki)?;      // 2048 to 8192 bits
rsa.check_pkcs1v15_sha256(&signing_input, &signature)?;

// DKIM verifiers must still validate 1024-bit keys (RFC 8301).
let dkim = RsaPublicKey::from_der_allow_1024(&p_value)?;
```

---

## Two errors, on purpose

- A signature that does not match (altered, wrong key, wrong message,
  wrong length) is `Error::AuthenticationFailed`, like every
  `*_check` in crypt-io, so `key.check(..)?;` rejects a forgery.
- A key that cannot be parsed, is not RSA (or not Ed25519), or has a
  modulus outside the accepted range is `Error::Sign`.

DKIM reports these differently (`fail` versus `permerror`, RFC 8601),
and a configuration error should not look like an attack in the logs.

---

## `Ed25519PublicKey` (feature `sign-ed25519`)

- `from_bytes(&[u8; 32])`, `check(message, signature)`, `to_bytes()`.
- `Clone`, `PartialEq`, `Eq`, `Debug` (hex), `Send + Sync`.
- Non-canonical signatures (`S` not reduced, RFC 8032 section 5.1.7)
  are rejected. Public keys of small or mixed order are accepted, as
  RFC 8032 allows; Wycheproof marks those 29 cases "acceptable". A
  signature under such a key proves little, but it cannot be forged
  for any other key.
- For DKIM `ed25519-sha256`, check against the SHA-256 of the
  canonicalized header data. The RFC 8463 example signature checks
  this way in `tests/verify.rs`.

## `RsaPublicKey` (feature `sign-rsa`)

- `from_der` (2048 to 8192 bits) and `from_der_allow_1024` (1024 to
  8192 bits), each taking a `SubjectPublicKeyInfo` or a bare PKCS#1
  `RSAPublicKey`.
- `check_pkcs1v15_sha256(message, signature)`: the message is hashed
  inside.
- `modulus_bits()`, exact, read when the key is parsed.
- `Clone`, `Debug` (modulus size), `Send + Sync`.
- **Strict encoding.** The signature must be modulus-sized and the
  padding and `DigestInfo` must be the exact DER RFC 8017 prescribes.
  BER-encoded padding, wrong hashes, a `DigestInfo` without its NULL
  parameter, malleated signatures: all rejected (all 249 invalid and
  all 3 "acceptable" Wycheproof 2048-bit cases).

**1024-bit keys, check only.** RFC 8301 requires DKIM verifiers to
validate keys from 1024 bits, and many domains still publish them, so
`from_der_allow_1024` exists. Use it only for DKIM: a 1024-bit key is
within reach of a well-funded attacker, so treat a pass as weaker
evidence. `from_der` keeps the 2048-bit floor that RFC 7518 sets for
`RS256`, and nothing in crypt-io signs with less than 2048 bits.

Keys are parsed once (`aws-lc-rs` `ParsedPublicKey`), so a JWT
verifier or a DKIM key cache pays only the verification per check.

## Speed

Same machine (Ryzen 9 9950X3D), 32-byte message, 2048-bit RSA, other
build sessions running in parallel:

| Operation | Linux (WSL2, gcc) | Windows 11 (MSVC) |
|---|---:|---:|
| `Ed25519SigningKey::sign` | 4.8 µs | 47 µs |
| `Ed25519PublicKey::check` | 23 µs | 153 µs |
| `RsaSigningKey::sign_pkcs1v15_sha256` | 192 µs | 225 µs |
| `RsaPublicKey::check_pkcs1v15_sha256` | 22 µs | 21 µs |

The crypt-io wrapper measured within noise of `aws-lc-rs` called
directly. AWS-LC's MSVC build does not use its s2n-bignum Ed25519
assembly, so Ed25519 is about 10 times slower on Windows; deploy
signing- or checking-heavy services on Linux. 1.3.0's notes gave only
the Windows Ed25519 signing figure (42 µs); `docs/PERFORMANCE.md` now
has both platforms.

## Compatibility

- **API:** additive. Two new types and one constant in `sign`.
- **Wire formats:** unchanged.
- **MSRV:** Rust 1.85, unchanged.
- **Features and dependencies:** unchanged; the checks use the same
  `sign-ed25519` / `sign-rsa` features and `aws-lc-rs` 1.19.

## Installation

```toml
[dependencies]
crypt-io = { version = "1.4", features = ["sign-ed25519", "sign-rsa"] }
```

On Windows x86-64 without NASM, add `"prebuilt-nasm"`.
