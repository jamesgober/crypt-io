# v1.3.0 — Signatures and PBKDF2

**Release date:** 2026-11-04
**Status:** stable minor release. Additive only; `cargo-semver-checks`
against 1.2.2 reports no semver break. No wire-format change. MSRV
stays 1.85. The default build is unchanged.

---

## What this release is

crypt-io has been symmetric-only. 1.3.0 adds the two pieces that mail
and token code needs on top of that, both behind features that are
off by default:

- a `sign` module with Ed25519 and RSA PKCS#1 v1.5 (SHA-256) signing,
  for DKIM (RFC 6376, RFC 8463) and JOSE (`EdDSA`, `RS256`);
- `kdf::pbkdf2_hmac_sha256`, the `Hi()` of SCRAM-SHA-256 (RFC 7677).

```toml
[dependencies]
crypt-io = { version = "1.3", features = ["sign-ed25519", "sign-rsa", "kdf-pbkdf2"] }
```

```rust
use crypt_io::kdf;
use crypt_io::sign::{Ed25519SigningKey, RsaSigningKey};

let ed = Ed25519SigningKey::from_pkcs8_der(&ed_pkcs8)?;
let dkim_b: [u8; 64] = ed.sign(&header_hash);       // ed25519-sha256
let dkim_p: [u8; 32] = ed.public_key();

let rsa = RsaSigningKey::from_pkcs1_der(&rsa_pkcs1)?;
let rs256: Vec<u8> = rsa.sign_pkcs1v15_sha256(&signing_input)?;
let spki: &[u8] = rsa.public_key_der();

let mut salted_password = [0u8; 32];
kdf::pbkdf2_hmac_sha256(password, &salt, iterations, &mut salted_password)?;
```

## Signatures

### Backend

The math is AWS-LC, through `aws-lc-rs` 1.19: the same backend
tls-net uses, so a binary that has both links AWS-LC once. crypt-io's
own types sit in front of it, and no `aws-lc-rs` type or error appears
in the API, so the backend can be replaced in 1.x without a breaking
change.

### `Ed25519SigningKey` (feature `sign-ed25519`)

- `from_pkcs8_der(&[u8])`: PKCS#8 v1 (what `openssl genpkey -algorithm
  ed25519` writes) or v2. A v2 document that carries a public key must
  match its private key.
- `from_seed(&[u8; 32])`: the RFC 8032 private seed.
- `sign(&[u8]) -> [u8; 64]`: pure Ed25519, deterministic.
- `public_key() -> [u8; 32]`: the DKIM `p=` value (base64) or JWK `x`
  member (base64url).

For DKIM `ed25519-sha256`, sign the 32-byte SHA-256 of the
canonicalized header data. `tests/sign.rs` rebuilds the RFC 8463
example message's header data and gets the RFC's `b=` value bit for
bit.

### `RsaSigningKey` (feature `sign-rsa`)

- `from_pkcs8_der` (`-----BEGIN PRIVATE KEY-----`) and
  `from_pkcs1_der` (`-----BEGIN RSA PRIVATE KEY-----`).
- `sign_pkcs1v15_sha256(&[u8]) -> Result<Vec<u8>>`: RSASSA-PKCS1-v1_5
  with SHA-256; the message is hashed inside. AWS-LC's blinded,
  constant-time RSA.
- `modulus_bits() -> u32` (exact, from the modulus) and
  `public_key_der() -> &[u8]` (DER SubjectPublicKeyInfo). Both are
  computed once when the key is parsed.

**Key sizes: 2048 to 8192 bits.** Anything smaller is refused when the
key is parsed, with `Error::Sign("key rejected: RSA modulus smaller
than 2048 bits")`. This is AWS-LC's limit and NIST SP 800-131A's rule
for signature generation. DKIM verifiers still accept 1024-bit keys
(RFC 8301), but crypt-io will not sign with one; the RFC 8463 example
RSA key, which is 1024 bits, is refused in the tests.

No `rsa` crate is involved, so RUSTSEC-2023-0071 (the Marvin timing
attack in `rsa`) does not apply and needs no audit ignore.

### Key handling

- Private keys live inside AWS-LC, which cleanses every allocation
  when it frees it, so dropping a key wipes it. crypt-io holds no copy.
- The bytes you parse a key from stay in your buffer. Wipe them with
  `crypt_io::wipe` once the key is built.
- `Debug` prints the Ed25519 public key or the RSA modulus size, never
  private material.
- Both types are `Send + Sync`: one key can sign from many threads.

### Cost of the features

| | `sign-ed25519` / `sign-rsa` |
|---|---|
| C compiler | required on every platform |
| NASM | required on Windows x86-64, or enable `prebuilt-nasm` (uses assembled objects shipped with `aws-lc-sys`) |
| `std` | required (the features turn it on) |
| MSRV | 1.85, unchanged (`aws-lc-rs` 1.19 declares 1.71) |
| First build | about 16 s debug / 24 s release extra on a 32-core machine; later builds reuse it |
| Dependencies | `aws-lc-rs`, `aws-lc-sys` and their build tools (`cc`, `cmake` crate, `jobserver`, ...); `sign-rsa` also `untrusted` |

Without NASM and without `prebuilt-nasm`, a Windows x86-64 build stops
in the `aws-lc-sys` build script with "NASM command not found". The
default build, `preset-minimal` and `preset-all` include none of
this.

### Not in 1.3

Verification, key generation, RSA-PSS and ECDSA. Verify with
`aws-lc-rs` or `ring` directly for now.

## PBKDF2-HMAC-SHA256 (feature `kdf-pbkdf2`)

`kdf::pbkdf2_hmac_sha256(password, salt, iterations, out: &mut [u8])`
implements RFC 8018 section 5.2 with HMAC-SHA256.

- `iterations` must be 1 to `kdf::PBKDF2_MAX_ITERATIONS` (10,000,000).
  0 is `Error::InvalidInput`, anything above the ceiling is
  `Error::LimitExceeded`, and both are checked before any work. A SCRAM
  server or a stored hash picks the count, so this keeps one call from
  tying up a thread for minutes. Ten million iterations take about
  0.65 s per 32-byte block on the reference machine; apply a tighter
  policy of your own on top (smtp-net uses 4,096 to 1,000,000).
- `out` is any length from 1 byte (usually 32,
  `kdf::PBKDF2_SHA256_OUTPUT_LEN`); each further 32 bytes costs another
  full run of iterations. `out` is untouched on error.
- Built on crypt-io's own HMAC and `sha2`'s compression function. No C,
  no new dependency, works without `std`, and the `hmac` / `hkdf`
  crates stay out of the graph (RUSTSEC-2026-0385).
- With `zeroize`, the key-derived SHA-256 states and every
  intermediate block are wiped before the function returns.

**Speed.** After the first block, every iteration is two SHA-256
compressions on the precomputed `K ^ ipad` / `K ^ opad` states, with a
block whose padding never changes. Measured on the reference machine
(Windows 11, Rust 1.99, other build sessions running at the same
time):

| Iterations | crypt-io | Per iteration |
|---:|---:|---:|
| 4,096 | 265 µs | 65 ns |
| 600,000 | 38.9 ms | 65 ns |

Interleaved in one process against `aws-lc-rs`'s PBKDF2 (600,000
iterations, three rounds): crypt-io 40 to 43 ms, AWS-LC 52 to 71 ms,
same output. crypt-io was 1.27 to 1.65 times faster.

PBKDF2 is not memory-hard. Keep Argon2id for new password storage and
use PBKDF2 where a protocol or stored format requires it.

## Proof

| Source | What is checked |
|---|---|
| RFC 8032 section 7.1, tests 1, 2, 3, 1024, SHA(abc) | Ed25519 public key and signature from the seed, and from PKCS#8 v1 and v2 |
| RFC 8463 appendix A | the `ed25519-sha256` DKIM-Signature `b=` value, rebuilt from the example message |
| NIST CAVP SigGen15 (FIPS 186-3), `[mod = 2048]` and `[mod = 3072]`, all 20 SHA-256 cases | RSA PKCS#1 v1.5 signatures from PKCS#1 and PKCS#8; exact SPKI and modulus size |
| RFC 8463 appendix A.1 RSA key (1024 bits) | refused |
| RFC 7914 section 11, RFC 6070 inputs with SHA-256 | PBKDF2 outputs, up to 80,000 iterations |
| Python `hashlib.pbkdf2_hmac`, 64 cases | password, salt and output lengths around the 64-byte block |
| RFC 7677 section 3 | SCRAM-SHA-256 SaltedPassword, ClientProof and ServerSignature |
| proptest, 256 cases | PBKDF2 against a direct RFC 8018 implementation over the public HMAC |

The NIST files give only `n`, `e` and `d`; the generator recovers `p`
and `q`, builds the DER encodings, and checks every published
signature with `S^e mod n` before writing it out. Generators:
`tests/data/gen_sign_vectors.py`, `tests/data/gen_pbkdf2_grid.py`.

## Other changes

- `Error::Sign(&'static str)` (the enum is `#[non_exhaustive]`).
- `kdf-all`, and so `preset-all`, now includes `kdf-pbkdf2`.
  `preset-all` is "every pure-Rust feature" and does not include the
  `sign-*` features.
- README: the MSRV note recommended `cargo update -p ctutils --precise
  0.4.2`, the version RUSTSEC-2026-0385 affects. `ctutils` is not in
  the graph since 1.2.2. A Rust 1.85 to 1.87 build with resolver 2
  needs `cargo update -p sha2 --precise 0.11.0` instead (checked:
  with that pin, a newest-versions resolution builds on 1.85 with
  `preset-all` and both `sign-*` features).
- `docs/SECURITY.md` no longer says crypt-io ships no PBKDF2; the
  README and architecture docs no longer send signatures to other
  crates.
- CI: a "Feature sets (sign, pbkdf2)" job runs clippy and the tests
  for each new feature on its own (stable and 1.85); the
  partial-feature doc job builds `kdf-pbkdf2`, `sign-ed25519` and
  `sign-rsa`; the `thumbv7em-none-eabihf` build includes `kdf-pbkdf2`;
  Miri now runs PBKDF2's unit tests and uses `preset-all` instead of
  `--all-features`, because Miri cannot execute AWS-LC's C code.
